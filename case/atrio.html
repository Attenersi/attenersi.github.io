§ 01 The brief

A tenant writes a sentence. Someone has to write a ticket.

Facility-management teams sit between two pieces of friction. On one side: a tenant who wants a problem fixed and has neither the patience nor the vocabulary of the building's documentation. On the other: a helpdesk operator who has to translate "the lift on the second floor is making a noise" into the right category, priority, contractor reference, and ticket. Between them sits a 200-page DOR, a procedure binder, and someone's tribal knowledge of which vendor handles which contract.

Atrio is what I think the middle should look like. A chat interface for the tenant or helpdesk, an LLM grounded in the building's own documentation, and a backend that turns the conversation into a structured ticket — automatically, with the right category and priority, and with citations to the source pages it used to decide.

I'm building this solo. It's a portfolio project and an open-source one. The chatbot works. The retrieval works. The interesting problem — and the reason for this case study — is everything between the two.

§ 02 What's built

The chat is the visible third of the product.

The user-facing surface is a chat interface. A question goes in, an answer streams out with the sources it consulted, and if the conversation contained a reportable issue, one or more tickets are filed in the dashboard. That's roughly two-thirds of what's in the repository today. The other third is the admin half: documents, knowledge gaps, RAG evaluation, training review, prompt-quality controls, and LLM profile management. The interesting work lives on that side.

What's working now
  • Chat with streaming responses — Next.js frontend, FastAPI backend, OpenAI-compatible provider integration
  • RAG over building documentation with cited sources surfaced in the answer (used_sources)
  • Auto-ticket creation from a single prompt — including multi-issue messages that produce multiple tickets
  • "Create ticket anyway" fallback for cases the model didn't classify confidently
  • Ticket dashboard with filters, statuses, CSV export
  • Admin console — documents, knowledge gaps, users, RAG eval runs, training review, LLM profiles
  • Prompt-injection & sensitive-output guardrails at the boundary
§ 03 Retrieval

Retrieval was the easy part — and that surprised me.

The first thing that gets attention in any RAG build is the retrieval layer: pick a vector store, embed the documents, query, return chunks, hand them to the LLM. I'd read a dozen papers and twice as many blog posts before I wrote a line. The stack came together quickly. Chroma running locally, persistent, with FM documents indexed from a seed set (a demo building called "Meridian Business Center"). Queries land, top-k chunks come back, the prompt includes them, the answer comes out with the sources listed.

That was a working chatbot inside the first two weeks. It was also a misleading milestone.

"Retrieval gets you to 'an answer.' It doesn't get you to 'the right one.'"

What I underestimated is how much quality lives outside the retrieval layer. Chunking strategy — the unglamorous decision of where to split a document — moves answer quality more than swapping embedding models. Reranking the candidates before they go into the prompt does more than tuning the top-k. And once retrieval is doing its job, the conversation isn't about retrieval anymore. It's about what the LLM does with the chunks. Which is mostly the next section.

§ 04 Decisions

The hardest call is whether to file a ticket at all.

A tenant message looks something like: "Hi, the meeting room on 3 is freezing and also the printer near reception is jammed again. Can someone take a look?" Two unrelated issues, different categories, different priorities, in one sentence. Sometimes there's no issue — just a question ("what's the wifi password for guests?"). Sometimes the issue is hidden — a question that contains an incident ("do we have a procedure for when the door alarm goes off at night, because it just did"). And sometimes the message is adversarial — a prompt-injection attempt dressed as a complaint.

Each of those needs a different outcome:

  • Multi-issue → one ticket per issue, classified independently
  • Pure question → answer with sources, no ticket
  • Hidden incident → answer the question and open a ticket
  • Injection → refuse, log, do not touch the ticket layer

My current approach is hybrid by design. The LLM returns a structured JSON describing what it thinks the message is — intent, issues, suggested categories and priorities. The backend then runs that JSON through a layer of guardrails and rules before anything is committed: deduplication against open tickets, priority caps for certain categories, category overrides, injection-pattern checks. The LLM proposes; the backend disposes. Function-calling APIs would have been a cleaner abstraction in theory, but I wanted the rule layer to be inspectable, version-controlled, and editable without redeploying a model integration.

"The LLM proposes. The backend disposes. The rules are version-controlled and the model integration isn't."

This is also where most of the iteration time goes. Retrieval quality is a slow drift you measure once a week. Decision quality is what changes the moment you add a new category, a new building, or a new edge case.

§ 05 The decision layer

The rules live in code, not in the prompt.

If retrieval is the easy third and the chat is the visible third, the decision layer is the part that actually matters and nobody asks to see. It's the code that stands between what the model proposes and what the system commits: deduplication against open tickets, priority caps on certain categories, category overrides, the injection refusal path. The model hands over a structured guess about what a message is; this layer decides what, if anything, happens because of it. Putting those rules in version-controlled code rather than in a prompt is a deliberate choice — I can read them, test them, and change one without renegotiating with a model integration.

This is also the part that has to be defended rather than merely built. A model that confidently misclassifies one message in fifty is invisible at demo time and dangerous at scale. So the layer is mostly subtraction: things the model is not allowed to do on its own. Open a duplicate ticket on an issue that's already tracked. Escalate a routine category to top priority. Act on a message that's really an injection attempt wearing a complaint. Each of those is a rule, not a hope.

"The interesting part of an LLM product isn't what the model can do. It's what you've decided it isn't allowed to do on its own."

An eval suite keeps this layer honest. There's a file of hand-curated cases — the messages I want to behave a specific way — and a runner that scores the system against them. I watch two numbers: one for whether the system responded at all, and one for whether it responded correctly once transport failures are stripped out. The first tells me it's up. The second tells me it's right. The loop is simple and the whole point: difficult conversations get reviewed, the ones that exposed a weakness become new test cases, a rule or prompt gets edited, the suite re-runs. If the correctness number goes up, the change is the new baseline. If it doesn't, the change was wrong and I revert it. The eval isn't the product — it's the thing that stops me from lying to myself about whether the decision layer got better.

§ 06 Roadmap

What's next. What I'm not building.

The next two weeks are about quality, not features. Better reranking before the LLM sees the chunks. Tighter rules on the categories that misclassify most. A more complete admin-review flow so that fixing a bad decision takes minutes instead of a deploy. Concretely: I want the correctness score on the eval set to move by a measurable amount before anything new goes in.

Deliberately not in scope.

Enterprise plumbing. No SSO. No multi-tenant isolation. No SOC 2-shaped paperwork. Those are problems for a product that has paying users; Atrio doesn't, and I'm not pretending otherwise.

Heavy analytics. A Power BI-style operational dashboard is the kind of thing you build when the core decisions are reliable. Mine aren't there yet.

UX polish. The interface looks like what it is — a developer's working environment. It can be made beautiful later. Right now beauty would be a way to avoid harder work.

The bet is that decision reliability is the only thing worth optimising at this stage. Everything else is a distraction dressed as progress.

§ 07 Lessons, in real time

The papers don't tell you the second half.

Building this changed my mental model of what a RAG project actually is. The papers describe the retrieval architecture beautifully and stop there. The real work is on the other side of the chunk-fetch: how you carve the documents up, what you put before and after the retrieved context in the prompt, what you do with the output before it touches the rest of your system, and how you measure whether yesterday's change broke today's behaviour.

The other thing I wasn't ready for is how much of the work is defensive. A model that confidently misclassifies one message in fifty is not a problem at demo time and is a serious problem at scale. So a real share of the build has gone into guardrails — patterns for injection attempts, deduplication checks, priority caps, category overrides, a refusal layer for things the model shouldn't act on. None of this is glamorous. All of it is the difference between a working prototype and a system you'd let near a real ticket queue.

If I had to compress the experience into one sentence: standing up an LLM is no longer hard. Controlling its behaviour on messy real-world input is the entire job.
